# Tcal 数据自动更新计划

## 目标

定期检查 FAST 官网的噪声二极管标定报告，在发现新数据后完成下载、转换、验证和发布。

数据流程：

```text
FAST 官网发布页
    -> 检查文章及下载链接
    -> 下载 PDF、high 和 low 原始数据
    -> 校验并安全解压
    -> 转换为 HiFAST 使用的 FITS
    -> 与最近 3 个正式发布版本绘图比较
    -> 生成 MD5、ZIP 和清单
    -> 发布 GitHub Release
    -> 上传数据 ZIP 至 Cloudflare R2
    -> 更新 main 分支的 manifest.json 和 sources.json
    -> 将同一个 manifest.json 上传至 Cloudflare R2
```

## 当前状态

- 官网发布页是 JavaScript 单页应用，文章数据来自加密的后端接口。
- 2026 年 7 月 13 日发布了 `Noise Diode Calibration Report-202607`。
- 该报告对应的实际标定日期是 `20260708`。
- 原始数据文件为 `high_202607.tar.gz` 和 `low_202607.tar.gz`。
- 当前 `manifest.json` 最新日期是 `20251101`，尚未包含 `20260708`。
- 现有转换过程保存在 `Tcal_convert` 各日期目录的 `convert.ipynb` 中，包含硬编码日期和交互式 Shell 命令，需要改写为普通 Python 程序。

## 处理规则

### 更新检查

- 定期读取官网分类下的全部文章，不能只检查第一篇。
- 保存文章 ID、更新时间、PDF 链接、high/low 链接和文件 SHA256。
- 优先从 PDF 文件名提取完整的 `YYYYMMDD` 日期。
- 下载 PDF，并从包含测试或测量描述的正文中提取实际测试日期。
- PDF 文件名包含完整日期时，正文日期必须与文件名日期一致。
- 文件名只有 `YYYYMM` 时，可以使用正文中唯一且明确的测试日期。
- 不能使用 `manifest.json` 推断新数据的日期。
- 正文日期缺失、存在多个可能日期或与文件名冲突时，停止自动处理。
- 区分新日期、链接变化和相同日期文件内容变化。

### 下载

- 设置连接超时、读取超时和重试。
- 使用临时目录，不把原始压缩包提交到 Git。
- 下载后计算 SHA256。
- 安全解压 tar 文件，拒绝绝对路径、`..` 和符号链接。
- high 和 low 数据都必须包含 `freq.dat`、19 个波束及每个波束的 a/b 文件。

### 转换

提供参数化命令：

```bash
python -m tcal_pipeline.convert_tcal \
  --date 20260708 \
  --high high_202607.tar.gz \
  --low low_202607.tar.gz \
  --output build/20260708
```

目标 FITS 结构：

- `FREQ`：65536 个 `float64`
- `TCAL`：形状为 `(19, 65536, 2)` 的 `float32`
- high 和 low 各生成一个 FITS

不能为了满足长度要求而静默裁剪数据。只有经过既有数据验证的兼容规则才允许使用；其他结构变化应终止处理。

### 验证

- high/low 两个 FITS 均可由 Astropy 打开。
- 频率长度为 65536、严格递增，且 high/low 频率一致。
- TCAL 形状为 `(19, 65536, 2)`。
- 数据中没有 NaN 或 Inf。
- 19 个波束及两个偏振完整。
- MD5 与生成的 FITS 一致。
- ZIP 可以通过完整性测试。
- 使用既有日期进行回归验证，防止转换规则改变已有数据含义。
- 选择当前日期之前最近 3 个正式发布版本，生成 high/low、XX/YY 的
  19 波束频谱对比图。
- 生成 1330–1430 MHz 范围内各波束相对 M01 的对比图。
- 图片作为人工辅助检查材料，不使用固定变化阈值自动判断标定结果。
- 绘图规则见 `VISUAL_VALIDATION.md`。

### 发布

周期任务自动完成检查和发布：

1. 每周检查 FAST 发布页；没有新日期时不下载、转换或绘图。
2. 发现新日期后下载、转换并执行全部结构与哈希检查。
3. 创建日期标签对应的 GitHub Release；数据 ZIP、5 张辅助图片和 JSON 摘要分别作为独立资产上传。
4. 将同一个数据 ZIP 上传到 R2；同名 R2 数据对象不允许用不同内容覆盖。
5. 更新 `manifest.json` 和 `sources.json`，提交并 push 到 `main`。
6. 最后把 main 中同样内容的 `manifest.json` 上传到 R2。

上述顺序保证 manifest 不会指向尚未存在的数据。如果中途失败，重新运行会复用内容完全一致的 Release 和 R2 ZIP；发现同名文件哈希不同则停止。

数据 ZIP 必须始终使用 `YYYYMMDD.zip` 文件名。添加图片时禁止重新打包或覆盖数据 ZIP，确保 HiFAST 使用的下载网址保持为：

```text
https://github.com/jyingjie/hifast-tcal-data/releases/download/YYYYMMDD/YYYYMMDD.zip
```

R2 数据路径只接收与标签同名的 `YYYYMMDD.zip`，不上传 PNG 或审核 JSON。

同一日期的数据不允许自动覆盖：

- URL 变化但 SHA256 不变：只更新来源记录。
- SHA256 变化：停止自动发布并要求人工确认。
- 确认需要保留两个版本时，可使用 `YYYYMMDD-r2` 等修订标签。

## 实施阶段

### 第一阶段：转换程序

- 将 notebook 中的有效逻辑整理为 `tcal_pipeline/convert_tcal.py`。
- 明确输入文件结构和 FITS 数据类型。
- 使用 `20241029` 或 `20251101` 做回归验证。

### 第二阶段：官网检查

- 实现官网加密接口客户端。
- 获取分类列表和文章详情。
- 提取 PDF、high 和 low 链接。
- 增加 PDF 文件名和正文日期解析、交叉检查及来源状态文件。

### 第三阶段：本地流水线

- 串联检查、下载、安全解压、转换、验证和打包。
- 增加只检查和完整试运行模式。
- 使用 `20260708` 完成试运行，但不发布。

### 第四阶段：周期任务

- 每周一北京时间 10:00 自动检查。
- 支持 `workflow_dispatch` 手动运行。
- 没有更新时正常结束。
- 官网接口变化、下载失败或转换失败时明确报错。

### 第五阶段：发布

- 周期任务发现新日期后自动创建 GitHub Release。
- 数据 ZIP 先发布至 GitHub 和 R2，再更新两份 manifest。
- 保留单个 Release ZIP 的手动 R2 恢复任务。

## 默认决定

- 检查频率：每周一次，并支持手动运行。
- 自动化程度：发现新日期后自动下载、转换、验证和发布。
- 原始文件：不提交到 Git，记录 URL 和 SHA256。
- 已有日期发生变化：禁止自动覆盖。
- 首个试运行目标：`20260708`。
